For decades, we taught C++ with two containers:

std::vector and std::map

That's wrong.

Pause for effect. "vector is king, but map is no longer its queen."

Why "unordered" and not "hash"? Quick history:

  • SGI era (late 1990s): SGI's STL shipped a non-standard hash_map; vendors like MSVC and GCC carried it as an extension.
  • TR1 (2005): introduced std::tr1::unordered_map — named "unordered", not "hash", to avoid clashing with those vendor hash_map extensions and to leave room for non-hash implementations.
  • C++11 (2011): standardized as std::unordered_map.

If std::vector is our default sequence container...

What is our default associative container?

Round 1

map vs. unordered_map

std::map — Red-Black Tree

  • Guaranteed O(log n) lookup, insert, delete
  • Keys always sorted
  • Node-based: pointer-chasing, cache-unfriendly
  • Stable iterators/references across all operations
"This is what we all learned. It works. It's predictable. But log(n) adds up at scale."

What is a Red-Black Tree?

red black nil sentinels not shown

Self-balancing → height stays ≈ log n

⇒ guaranteed O(log n) lookup / insert / erase

Every node is a separate heap allocation

Coloring keeps the longest path ≤ 2× the shortest — that's the balance.

"A red-black tree is just a balanced binary search tree. The colouring is the bookkeeping that keeps it balanced: any root-to-leaf path is at most twice the shortest, so height stays around log n and lookups are guaranteed O(log n). That's the upside — predictable and ordered. The catch is the last bullet, and it's the thread for the rest of the talk: every node is its own heap allocation, so walking the tree is pointer-chasing across scattered memory — a cache miss per hop. Hold that thought: it's exactly why the hash table beats it here, and why the FLAT maps in the open-addressing section win even bigger. (nil sentinels are conceptual null children — not stored; that's why I don't draw them as real nodes.)"

std::unordered_map — Hash Table

  • Average O(1) lookup, insert, delete
  • Keys unordered
  • Bucket-based: separate chaining (linked lists)
  • "Average" is doing heavy lifting in that sentence
Emphasis on "average-case" — this is foreshadowing for the pitfalls section.

One honest caveat

O(1) is in the number of elements — not free.

unordered_map: every lookup hashes + compares the whole key → O(k) in key length k

map: O(k · log n) — the comparisons add up too

For long string keys, hashing cost is real. The win is in n, not in k.

"I want to be honest before someone in row three is. The flat line is flat in N. But every lookup still pays to hash the full string — that's O(k) in key length. map pays O(k) per comparison times log n comparisons. So unordered_map wins as N grows, but neither is free on long keys. Keep your keys short."

Separate Chaining

Bucket 3 (head of linked list):

"MID_100001" →

"MID_500099" →

Each bucket is the head of a linked list.

When two keys hash to the same bucket, they get chained.

"This isn't an accident. The standard's bucket API + reference stability across rehash force each element into its own heap node. That IS separate chaining — and it's why the faster maps we'll see later had to ship as separate libraries: they break this guarantee."

O(1) assumes each bucket has ~1 item.

O(n) happens when one bucket has ALL items.

"This is the entire talk in two sentences. Everything that follows is about what makes buckets overflow."

Load Factor


load_factor = size() / bucket_count()

When load_factor > max_load_factor (default: 1.0)

REHASH: Allocate new bucket array → re-hash every key → re-link all nodes
• Rehash = stop-the-world: new bucket array, re-hash + re-link every node • max_load_factor tunes collision vs memory — lower = faster/fatter, higher = slower/leaner • Almost everyone uses it wrong: they want reserve(), not load factor tuning • Matt Kulukundis (CppCon 2017) audited every load-factor user at Google — all wrong; SwissTable made set_max_load_factor a no-op • Practical advice: call reserve() if you know the size, leave max_load_factor at 1.0, profile before touching it

Pitfall 0: It's in the name

The next three pitfalls cost you performance.

This one costs you correctness — and it bites first.

"Before we talk about speed, the scariest swap bug has nothing to do with speed. unordered_map is unordered. If any code relied on the order, swapping it silently changes behavior — and it compiles, and it passes a quick test."

A real auth service

A per-request std::map is iterated in order to build the wire message…


std::string requestMapToMML( std::map<std::string,std::string>& req ) {
    std::string mml;
    for ( const auto& field : req ) {        // sorted iteration
        mml.append( toMmlTag(field.first) );
        mml.append( field.second );
        mml += MML_FIELD_SEP;
    }
    mml += Crypto::SHA1( mml );               // order is now in the hash
    return mml;
}

Swap to unordered_map → fields reorder → bytes change → SHA1 changes → the switch rejects the message.

distilled from a real payment-auth service · src/22_ordering_is_load_bearing.cpp

"This is real, lightly distilled. The map's iteration order WAS the wire format, and it's baked into a SHA1. One container swap and every message fails integrity at the far end."

    }

"Four fields. We need to hash this to use it as a key in our unordered_map."

Bad Hash vs Good Hash

BAD 

struct BadHash {
  size_t operator()(
    const Transaction& t) const {
    return std::hash<std::string>{}
      (t.currency);
  }
};
// Only hashes currency
// 99% "USD" → collision!
GOOD 

struct GoodHash {
  size_t operator()(
    const Transaction& t) const {
    size_t seed = 0;
    // Order-dependent mixing:
    mix(seed, t.merchant_id);
    mix(seed, t.card_bin);
    mix(seed, t.amount_cents);
    mix(seed, t.currency);
    return seed;
  }
};

Why not plain seed ^= hash(field)? XOR is commutative — swap merchant/BIN and you get the same hash. mix() is on the next slide.

src/04_pitfall1_bad_hash_txn.cpp

"Left: only hashes currency. 99% USD means 99% collision. Right: combine ALL fields — but HOW you combine matters. Plain XOR is commutative and self-cancelling: hash(A,B) == hash(B,A), and two equal fields XOR to zero. That's why we use an order-dependent mix() — shown next as hash_combine. The source file uses exactly that."

The Pro-Tip: hash_combine


template <typename T>
void hash_combine(size_t& seed, const T& val) {
    const size_t GOLDEN = 0x9e3779b9;
    seed ^= std::hash<T>{}(val) + GOLDEN
            + (seed << 6) + (seed >> 2);
}

template <typename... Args>
inline size_t hash_values(const Args&... args) {
    size_t seed = 0;
    (hash_combine(seed, args), ...);  // C++17 fold expression
    return seed;
}
    

struct TransactionHash {
    size_t operator()(const Transaction& t) const {
        return hash_values(
            t.merchant_id, t.card_bin, t.amount_cents,
            t.currency, t.timestamp_ms);
    }
};

When O(no-no-no) becomes a CVE

HashDoS: collisions as a weapon

"Pitfall 2 was an accident. Now imagine an attacker doing it ON PURPOSE. This section is the elastic one — if I'm behind, I'll trim the CVE list; if I'm ahead, I linger on mitigations."

The attack

1. Your server puts user input into an unordered_map (form fields, JSON keys, headers).

2. The attacker knows your hash — it's open source.

3. They send keys crafted to all collide into one bucket.

4. Every insert/lookup is now O(n). One small request burns 100% CPU.

A few hundred KB of crafted keys can pin a core for minutes.
"It's a denial-of-service with an almost-free payload. The asymmetry is the danger: tiny request, enormous server cost."

This is not hypothetical

28C3, Dec 2011 — Klink & Wälde, "Efficient DoS on Web Application Platforms." One talk, many languages.

The fix the ecosystem chose: randomized hashing. Python adopted SipHash + a random seed (PEP 456).

"Every major web platform was vulnerable at once because they all used predictable string hashes. The industry-wide response was to randomize the hash."

Mitigations


// Per-process random salt: attacker can't precompute collisions
static const uint64_t kSalt = seed_from_os_rng();
struct SaltedHash {
    size_t operator()(const std::string& s) const {
        size_t h = std::hash<std::string>{}(s);
        return h ^ (kSalt + 0x9e3779b97f4a7c15ULL + (h<<6) + (h>>2));
    }
};

Randomized/keyed hash (SipHash) — the real fix. Salt changes every run.

The paradox: reserve() also helps — fewer rehashes = a smaller attack window.

Untrusted keys? Cap them, or fall back to a sorted container under load.

src/20_randomized_hashing.cpp

hash_combine (src/05) solves distribution: mixes multiple fields into one well-spread hash. But seed=0, deterministic every run. An attacker who knows your hash can precompute collisions offline. SaltedHash (src/20) solves predictability: per-process random salt means the attacker can't know the output. They're complementary. Production does both: combine fields properly AND mix in a random salt. reserve() callback from pitfall 3: fewer rehashes = smaller attack window. Don't hand-roll crypto. Use a vetted keyed hash (SipHash).

src/11_iterator_stability_txn.cpp

Iterators break because rehash rebuilds the bucket linked-list wiring. The nodes stay at the same address (pointers safe), but the next/prev links change (iterators stale). If your system holds iterators across insertions, std::map is the correct choice.

Open Addressing

Why your hot path might not want std::unordered_map

Node-based chaining means every collision step chases a pointer to a random heap address. On a lookup-heavy hot path (millions of BIN lookups/sec), that's a cache miss on every probe. Open-addressing alternatives (SwissTable, flat_hash_map) store keys contiguously, so probing stays in cache. Typically 2x+ faster. unordered_map isn't always the answer in either direction: need stability, use std::map. Need speed, use a flat hash map.

Why chaining hurts

Standard unordered_map = bucket array → heap-allocated nodes in a linked list.

Every collision step is a pointer chase to a random address → likely cache miss.

Remember: the standard's bucket + stability guarantees force this layout.

bucket[] → node@0x7f3a → node@0x91c2 → node@0x4b08 → ...
(each arrow = a jump to somewhere else in RAM)
"The container is correct and convenient, but cache-hostile by design. Chasing pointers to scattered nodes is the opposite of what modern CPUs want."

Open addressing: keys live in the array

No nodes. On collision, probe the next slot (linear / quadratic / SwissTable groups).

+ Contiguous memory, cache-friendly, no per-element allocation.

− Tombstones on erase, sensitive to load factor, and…

− references invalidate on any insert (a flat map rehashes constantly).

"This is the SwissTable idea Google open-sourced as abseil. Keys sit in one array; you probe forward on collision. You trade reference stability for cache locality."

Memory

Where O(1) goes to die: the cache

Two layouts

Node-based (map, unordered_map)

[bucket]→node→node
scattered across the heap
+ allocation header per node

Contiguous (flat_map, flat hash)

[k|k|k|k|k|k|k|k]
one array, one allocation
prefetcher-friendly
"Same logical data, completely different physical reality. The CPU loves the right-hand picture."

Same O(1) — but the constant grew ~19x as the table left cache.

Two more levers

Allocators: std::pmr::unordered_map + a pool/monotonic buffer keeps nodes close together — clawing back some locality. Great for fixed-size auth records.

Stdlib matters: libstdc++ vs libc++ vs MSVC differ on bucket growth, default max_load_factor, and node layout.

Same code, GCC vs Clang on this laptop → different memory + timings. Benchmarks don't transfer.

"Two practical takeaways: pmr allocators are an easy locality win for node-based maps, and never trust a hash-map benchmark from a different stdlib than the one you ship."

Hoisting the lock was 10 to 27x. Only after that does map-vs-unordered even show up. Always find the real bottleneck before you optimize the famous one."

Concurrency: it's not thread-safe

unordered_map — concurrent read+write is UB. Read-only concurrent access is fine.

One global mutex serializes everything. Sharding (N maps, N locks) restores parallelism:

4 threads, 75% readssingle mutexsharded ×16
throughput149.6 ms69.5 ms (2.15x)

Production: tbb::concurrent_hash_map, folly::ConcurrentHashMap. And a rehash mid-flight is especially dangerous.

"Two things people get wrong: they assume reads-with-writes are safe (they're not), and they put one mutex around a giant map and wonder why it doesn't scale. Sharding is the simple fix; for real workloads use a purpose-built concurrent map."

The Decision Framework

Choosing the Right Container

Rules[3]

std::vector is your default sequence.

std::unordered_map is your default associative container.

It is O(1) fast but O(no-no-no) dangerous.

0. Order → don't swap a map you iterate for output

1. Bad Hashes → use hash_combine

2. Collisions → hash ALL fields

3. Rehashing → call reserve()

…and measure — the container is rarely your bottleneck.

Your New Decision Tree

Pro tips when you land on unordered_map:   Custom key? → write a good hash (hash_combine).   Know the size? → call reserve().   Read-heavy + load-once? → consider flat_map or a flat hash map.
